About me

My trade is not using the models. It is making them work together.

I have worked with language models since before they became a mass-market product, and I have tested them as they came out ever since: today I keep sixteen configurations under comparison, from seven different providers, and I switch when the numbers justify it.

I design and build agent systems: from the first line to maintenance. I connect them to the company’s data and tools, I close them inside security boundaries that do not depend on the good will of the model, and I keep them in service over time. I work both with cloud models and with models that run locally, when the data must not leave the building.

What’s an agent

A model answers. An agent works.

It takes an objective, chooses which operations to call, checks the result and stops when it is done or when it cannot go further.

What I do

Not three things. One whole trade: building the system, closing it, connecting it to the data and keeping it standing.

01

Agents from scratch

I design and build both the agent and the agent’s boundary: objective, available operations, verification criteria.

 02

Agent teams

Several specialised agents that split the work and check one another. The one that executes is not the one that verifies.

 03

Tools and databases

I connect the agents to the data and the programs the company’s already using, with operations written one by one.

 04

MCP servers

I build and maintain the servers that expose those operations to the agents, with the permissions of whoever calls them.

 05

Security architectures

Permissions live in the database and in the operating system. Five levels, and the most fragile one is the layer of instructions.

 06

Deterministic answers on data

The model does not touch the data: it chooses among operations already written. Three outcomes, never confused.

 07

Local models

Choice of the parameter class, quantisation, fine-tuning on data from the client. Nothing leaves the machine.

 08

Automations and workflows

What is repetitive and verifiable gets automated: where judgement is needed, a person stays.

 09

Maintenance and verification

Periodic checks, regression tests, updating the models when the numbers move.

Security

Five levels, different strength

From the strongest to the most fragile. The last one guarantees nothing.

01   Database
02   Operating system
03   Execution isolation
04   Application rules
05   Instructions to the model No guarantee

The rule that is not up for negotiation

If a prohibition lives only in the instructions to the model, for the client it does not exist.

Data

Three outcomes, never two

Confusing the last two is the flaw that makes numbers get invented.

OutcomeNameWhat arrives
01 Data present It arrives as it is written in the data store, comparable with what was read.
02 Data absent Declared absent. Not reconstructed, not estimated, not rounded.
03 Read failed A visible error, never a plausible answer in place of a true one.

Automation

Agents that publish, flows that take away the repetitive work

What is repetitive and verifiable gets automated: where judgement is needed, a person stays.

What gets automated

Steps that repeat always in the same way
Waits, sends, conditions, fixed steps
Anything for which there is a way to check the outcome

What stays with a person

The exceptions nobody has written down
The decisions where judgement is needed
Watching over what runs on its own

Method · six rules

01

The deterministic part before the model.

02

Nothing is declared done without a test.

03

Better a visible error than a plausible, wrong answer.

04

Every agent has only the permissions it needs.

05

Client data stays with the client.

06

A system counts if it stays standing over time, not on the day of the demo.
