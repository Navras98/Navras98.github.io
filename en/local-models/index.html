Local models

The model that runs in-house

No data leaves the machine, and no bill per token. What it asks for in return is memory, and memory is a sum you do beforehand, not afterwards.

01

Arithmetic, not opinion

A model takes up memory in proportion to its parameters and to the number of bits each weight is stored in. That is where you start if you want to know whether a machine can cope, before downloading twenty gigabytes.

FP16about 2 GB per billion parameters
Q8about 1,06 GB per billion
Q5 / Q6about 0,62 GB per billion
Q4_K_Mabout 0,56 GB per billion
On topthe context cache, which grows with the length of the conversation

03

What you lose by compressing

Quantisation does not degrade everything in the same way, and the first part to give way is not the one people usually watch.

Q8No perceptible difference on text
Q4_K_MSmall loss on text, visible on maths and code
Below Q4Tool calls start to break: wrong format, invented parameters
ConsequenceFor an agent I count memory at Q5 or Q6, not at Q4

04

When local is worth it

It is not an ideological question. It is a question of where the data sits, how much work there is and how much quality is needed.

Worth it

The company’s data cannot leave the building
High volumes of simple, repetitive tasks
It has to work without a network too
Predictable cost: you pay for the machine, not for the token

Not worth it

Long reasoning on hard problems
Very long contexts on modest hardware
Few requests a day: the machine sits idle
Nobody to update and keep an eye on the system

The sum that always goes wrong

A model that fits in memory but leaves no room for context is not slow: it stops.

Stated limit

A local model does not match a frontier model on hard problems, and saying otherwise is dishonest. What it does well is bounded, repetitive work, with the data staying inside. Most of the systems I build use both, and the choice is made step by step.
