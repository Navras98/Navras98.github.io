Tools

What I work with, and what I do with it

Not a list of brands: for every tool there is the place it takes in the systems I build. The architectures are the public ones of the respective projects, not versions of my own.

I use and compare every model and every agent in circulation. Something new comes out every week: the choice has to be made again, not inherited. Trademarks belong to their respective owners and are named only to say which tools I use.

01

The tools and their place

An agent system is made of pieces that each do one thing. When one of them has to be replaced, that piece is replaced and not the system.

01 Execution base

OpenClaw

Open source environment for running agents connected to real tools. I use it as the base on which to build and supervise teams of agents: I give them tools, permissions and a log of what they have done.

Official site ↗
02 Agent on the code

Claude Code

Command line agent for working on the code of a project. I use it to build and maintain the systems I deliver, and to show in training how an agent works when it has the right permissions.

Documentation ↗
03 Boundary between model and tools
MCP

MCP servers

The protocol through which an agent sees the operations available instead of improvising them. I write the servers that expose to the model only the permitted operations: that is where the boundary runs.

Specification ↗
04 Autonomous agent

Hermes Agent

Open-source autonomous agent from Nous Research. I use it and benchmark it on multi-step tasks, where what counts is how an agent holds up when it is left to work on its own for many iterations.

Official site ↗
05 Workflows
n8n

n8n

Where the work is repetitive and verifiable, a workflow costs less than an agent and it’s more predictable when it breaks. Which of the two I use depends on the case, not on what I’m used to.

Official site ↗
06 Where the permissions live
SQL

PostgreSQL

The permissions sit in the database: roles, views, row level rules. An agent cannot read what its role does not see, whatever it is asked to do.

Official site ↗
07 Each run’s isolation
DOCKER

Docker

Every run sits in a container with its own resources and its own limits. If something goes wrong, it goes wrong inside a perimeter.

Official site ↗
08 When the data does not leave
LOCAL

Local models

When the constraint is that the data must not leave the network, the model runs on the client machine. The cost is in expertise, not in usage.

See the Models page →

02

How I put them together

The order matters more than the choice of pieces. An agent gets its tools from an MCP server, its permissions from the database and the operating system, and a log that says what it did and on what evidence.

ToolsAn MCP server in front of every operation
PermissionsRoles in the database, not sentences in the prompt
IsolationOne container per run
LogEvery action traces back to a read

The criterion

The tools change every month. The order they sit in does not.

Stated limit

None of these tools is mine, and I have no partnership with the people who make them: I use them, compare them and replace them when they stop being the right choice. If a project listed here changes its architecture, the way I use it changes too.
